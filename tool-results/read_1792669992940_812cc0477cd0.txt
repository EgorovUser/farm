    72→## 3. Фокус 1 — withEnergy: канонический контракт (для будущих модулей)
    73→
    74→Порядок операций по коду (energy.ts:79-90) и проверкам:
    75→
    76→1. **Резолв стоимости**: `cost = statBus.resolve('action.<sys>.<verb>.energyCost')` — всегда через шину (модификатор «Спартанец» M14 опустит цену без ведома модуля; floor + min 1 в meta баз).
    77→2. **Гейт upfront**: `energy < cost` → отказ ДО выполнения действия; состояние цело, событий ноль.
    78→3. **Действие**: `action()` выполняется только при пройденном гейте (обычно `transaction.transact`).
    79→4. **Отказ действия** → энергия НЕ тронута, событий расхода ноль («откатывается» ≡ «не списывается» — сильнее формулировки карточки §8 п.4, в безопасную сторону).
    80→5. **Списание после успеха**: атомарная проверка+мутация (JS однопотен) → **ровно одно** `player.energySpent {stat, cost, current, max}` + одно `player.energyChanged {delta: −cost}`.
    81→6. Повторный вызов/ретрай двойного списания не даёт (провал не списывает; успех списывает один раз — selftest `spentEvents === 1`).
    82→
    83→Каноническая формула для M02/M05/M07/M12/M13: **`withEnergy(statId, () => transaction.transact({...}))` — гейт → транзакция → списание → событие; энергия не тратится на отказавшее действие.** Оговорка композиции (не реализовано, не требовалось): вложенные withEnergy в одном действии могут уронить внешний спенд после успешного внутреннего — при появлении смешанных действий (крафт M09: материалы + энергия) ратифицировать «одно withEnergy на действие».
    84→
    85→Косметика: при вызове с кастомным reason поле `stat` payload'а `player.energySpent` несёт reason-строку, а не стат-id (energy.ts:54,69) — при штатном вызове без reason они совпадают.

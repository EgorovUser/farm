# 00 — README: как пользоваться набором промптов

> Набор «КОРНИ И РУДА» v2.0 — полное техническое задание браузерной игры (ферма + idle + карточный рогалик), оформленное как **модульный мега-промпт** для AI-кодинг-агента (Claude Code, Cursor, Copilot Workspace и т.п.).
> Автор концепции — заказчик. Систематизация, архитектура и стартовые числа — ИИ-дизайнер.
> **v2 — полная архитектурная переработка:** шины модификаторов как ядро, ривен-конструктор характеристик (Warframe-стиль), жёсткая изоляция модулей, план разработки «сначала механики и просчёты без интерфейса».

## 1. Почему набор, а не один файл

Проект велик (18 игровых модулей + ядро), а AI-агент за один сеанс надёжно осиливает один модуль среднего размера. Поэтому набор собран так, чтобы **один рабочий сеанс = один файл-модуль**, при этом каждый файл самодостаточен: в нём есть механики, формулы, схемы, интеграция и критерии приёмки. Набор заменяет прежнюю монолитную версию (v1) целиком.

## 3. Золотые правила передачи в AI

1. **Базовый контекст всегда:** `01-CORE` + `02-BUSES` (+ `03-DATA`, если задача трогает схемы).
2. **Один сеанс — один модуль.** Не просите «сделай ферму и рыбалку» — это два сеанса.
3. **Ядро заморожено.** Если задача модуля требует изменить контракт шин (`02-BUSES`) — остановите AI и пересоберите задачу сами.
4. **После каждого модуля:** запуск тестов, commit, короткий отчёт AI (что сделано, какие файлы, решения `[DECISION]`, вопросы `[QUESTION]`).
5. **Правки промптов помечайте** в самих файлах маркерами `[ДОБАВЛЕНО]` / `[ИЗМЕНЕНО]` / `[УДАЛЕНО]` с датой — набор версионируется как код.
6. **Числа не правятся в коде.** Любой баланс — правка таблиц в `content/balance/` отдельным сеансом.
7. **UI-полировка — только фаза 6.** До этого используется debug-консоль и минимальные отладочные панели из `02-BUSES §12`.

## 4. Шаблон запроса к AI (копировать и заполнять)

```
КОНТЕКСТ: [01-CORE] + [02-BUSES] + [03-DATA] (+ [04-DISCOUNTS], если модуль про цены)
ЗАДАЧА: Модуль M0X «Название» — реализация по спецификации.
СДЕЛАЙ: код модуля + контент-данные + тесты + debug-команды.
НЕ ЛОМАЙ: контракты шин, схемы ядра, сейв-версию, чужие модули (импорты запрещены).
ГРАНИЦА: делай ТОЛЬКО то, что описано в разделе «Границы модуля».
РЕЗУЛЬТАТ: работающие тесты + отчёт (файлы, [DECISION], [QUESTION]).
```

## 5. Анти-паттерны (запрещать AI в каждом сеансе)

1. Генерировать несколько систем за один ответ.
2. Придумывать числа в логике вместо `content/balance/`.
3. Мутировать базовые значения (база задаётся в данных один раз — навсегда; см. `01-CORE` П2).
4. Читать статы/цены/роллы в обход шин (см. `02-BUSES`).
5. Импортировать один игровой модуль из другого (см. `01-CORE` П4).
6. Менять имена типов и полей (глоссарий — `01-CORE §11`).
7. Менять модель сейва без миграции.
8. Прятать шансы и условия от игрока.
9. Начинать красивый UI раньше фазы 6.
10. Добавлять механики сверх ТЗ без метки `[РАСШИРЕНИЕ]`.

## 6. Если AI «не справляется»

Это нормально на проекте такого объёма. Сузьте шаг: не «сделай модуль M05 Ферма», а «сделай модель FarmTile и переходы состояний по M05 §3, тесты на переходы, без UI». Каждый файл-модуль специально нарезан так, чтобы сузить шаг можно было одной фразой. Если контекст сеанса переполняется — начните новый чат с базового контекста и только нужного модуля.

## 7. Что можно менять в наборе

- Числа и таблицы баланса (все — стартовые значения, живут в `content/balance/`).
- Порядок фаз 3–5 и содержание таблиц контента (списки рыб, мобов, культур).
- Формулировки интерфейса и названия на русском.

## 8. Что менять нельзя

- Архитектуру шин и правило неприкосновенности базы (`01-CORE` П2–П3, `02-BUSES`).
- Изоляцию модулей и каналы коммуникации (`01-CORE` П4, §7).
- Ривен-модель стоимости бафов/дебафов (M03) — её можно только расширять новыми типами модов.
- Версионируемый сейв с миграциями.

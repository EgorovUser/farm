# M09 — Крафт: станции, рецепты, качество результата

> Фаза 2 · объём M · вход: 01-CORE, 02-BUSES, 03-DATA, M01, M02, M15, этот файл.

## 1. Цель модуля

Крафт расширяется станциями — каждая открывает свои рецепты. Качество результата считается формулой от навыка, входов и мини-игры. Крафт — главный путь к предметам высокого тира и мост к заточке (M10).

## 2. Станции (покупаются как улучшения дома; данные)

| Станция | Рецепты |
|---|---|
| Рабочий верстак (старт) | лопата, лейка, плуг, Корм, Удобрение, Доски, Гвозди, ремонтный набор |
| Плавильня | руда → слитки; сплавы (медь + олово = бронза) |
| Наковальня | инструменты (кирки, топоры, удочки), оружие, броня, щиты; ремонт; вкладка ЗАТОЧКИ (M10) |
| Кожевенный верстак | кожа → броня, «Рюкзак» (+4 слота инвентаря), изделия из рыбьей кожи |
| Ткацкий станок | шерсть → ткани → одежда (бафы), знамёна |
| Кухня | урожай + рыба + яйца → еда (энергия/HP/временные модификаторы) |
| Алхимический котёл | зелья: боевые, роста, удачи; лекарства для рыб/животных |

## 3. Рецепты

`RecipeDef` (03-DATA §8): входы (ресурсы + предметы), энергия, время (секунды; очередь крафта — idle-элемент), выход, гейт `unlock`. Цепочки глубиной 2–4 шага: руда → слиток → пластины → кирка; брёвна → доски → гвозди → постройки деревни. UI-будущее: подсказка «где добыть недостающее» — из `sources` контента (03-DATA §11/M01 §4).

## 4. Качество результата

```
outputTier = round( 0.5 × avgInputTier + 0.4 × craftSkillTier + (−1..+1 за мини-игру) )
```

- Навык «Крафт» (M01) — через шину; мини-игра — MinigameContract с auto-режимом (0 по умолчанию до фазы 6).
- Качество входных ингредиентов влияет: еда из овощей тира S лучше.
- Результат — `ItemInstance` с качеством; стартовые ривен-роллы — если у шаблона есть `modSlots`, ролл через M03 в бюджете редкости.

## 5. Очередь и оффлайн

- Одна очередь на станцию (длина растёт улучшениями); время — абсолютные даты; catchUp досчитывает готовые партии и копит их до cap (данные: 6 партий).
- Отмена: возврат входов за вычетом 10% (мягко, cozy-правило).

## 6. Интеграция

- События: `craft.started`, `craft.completed` (defId, качество — для XP/навыка/квестов/ачивок).
- TaskRegistry: `craft.queue` (работник-кузнец).
- Провайдер: `craftStationProvider` (эффекты станций: «Мифриловая наковальня» — потолок заточки M10 как `cap`-модификатор).
- Debug: `craft.recipe <id>`, `craft.queue add <id>`, `craft.list <station>`.

## 7. Приёмка и тесты

- [ ] Рецепты из данных: неизвестный рецепт/станция — валидная ошибка; гейт-рецепт не крафтится.
- [ ] Формула качества покрыта тестами на сетке входов/навыка.
- [ ] Очередь в catchUp: фиксированные даты, cap переполнения, отмена возвращает входы.
- [ ] Наковальня реально ограничивает потолок заточки модификатором (интеграционный тест с M10 без импортов).
- Границы: заточка — M10; ривен-ролл — M03; цены — шина.

# 01 — CORE: роль, продукт, философия, архитектура, конвенции

> Подавать первым в КАЖДУЮ сессию. Файл задаёт роль AI, видение игры, железные архитектурные принципы (шины, изоляция, неприкосновенность базы), структуру проекта, правила файлов и глоссарий. Всё, что здесь запрещено, — запрещено безусловно; всё, что разрешено, — описано в `02-BUSES` и модулях M01–M18.

## 1. Роль

Ты — senior системный архитектор и full-stack разработчик игр. Ты строишь одиночную браузерную игру с нуля: ядро, данные, логика, тесты, позже — интерфейс. Ты работаешь итеративно: каждая завершённая задача оставляет проект в запускаемом состоянии, с зелёными тестами и без «TODO-заглушек в ядре». Ты НЕ генерируешь несколько систем за раз, НЕ придумываешь баланс в коде и НЕ обходишь архитектурные правила ниже — даже если «так быстрее».

## 2. Продукт (видение)

**«КОРНИ И РУДА»** — уютная экономическая RPG-инкубатор в браузере: гибрид фермерского симулятора, инкременталки и карточного рогалика. Референсы: Stardew Valley (цикл фермы), Moonlighter (контраст «свет наверху — мрак внизу»), Melvor Idle (панельная глубина систем), Warframe (ривен-система характеристик по бюджету), Path of Exile (дерево пассивок).

Игрок получает в наследство хутор у рудной горы. Наверху — грядки, пруд, скотный двор, кузница, магазинчик с ежедневным завозом. Внизу — многослойная шахта: мобы, боссы, карточные забеги, руда. Добытое внизу кормит экономику наверху: руда → слитки → инструменты → заточка → глубже. Лейтгейм — подъём соседней деревни: потребности жителей, налоги, биржа с окрестными поселениями.

Ядро цикла:

```
Энергия → действия (ферма, рыбалка, шахта)
        → ресурсы и предметы
        → крафт, заточка, разведение
        → продажа (магазин, биржа, деревня)
        → золото → работники, улучшения, снаряжение
        → гейты открываются (уровень, навыки, ачивки)
        → цикл повторяется глубже
```

Платформа: панельная игра-интерфейс (вкладки, таблицы, окна мини-игр), без аватара и свободного перемещения. Десктоп-first. Одиночная, сейвы локальные. Cozy-принцип: максимум потерь — 20% добытого за сессию; прогресс игрока не обнуляется.

## 4. Философия — шесть железных принципов

**П1. Данные ≠ код.** Весь контент — рыбы, культуры, мобы, рецепты, карточки, квесты, деревни, улучшения — это таблицы в `content/`. Логика — обобщённые механизмы, которые умеют обрабатывать ЛЮБОЙ контент по данным. Добавление новой рыбы = добавление строки JSON, а не кода. Если для нового контента пришлось править логику — логика спроектирована плохо, переделай.

**П2. База неприкосновенна.** Базовые стоимости, характеристики и любые числовые параметры задаются в данных ОДИН раз и НИКОГДА не мутируются никем и ни при каких условиях. `basePrice`, `energyCost`, `hp`, `growTime` и т.п. — константы данных. Любое изменение значения на практике — результат работы шины модификаторов (см. П3), которая берёт базу, применяет модификаторы и возвращает итог. Мутирующий базу код — ошибка архитектуры, а не «оптимизация».

**П3. Всё через шины.** Любой потребитель числа, на который могут влиять бафы/скидки/навыки/пассивки, получает его ТОЛЬКО через `bus.resolve(...)` (`02-BUSES`). Чтение базы напрямую из данных разрешено только самой шине. Продажи и покупки — только через PriceBus и TransactionService. Все рандом-роллы, влияющие на игрока, — только через RngBus (с удачей и сидами). События между модулями — только через EventBus.

**П4. Модуль знает только себя.** Игровой модуль ничего не знает о внутренней логике других модулей. Прямые импорты между M01–M18 ЗАПРЕЩЕНЫ. Разрешённые каналы: (а) публикация/подписка событий на EventBus; (б) запросы к шинам; (в) регистрация и запрос исполнителей в TaskRegistry; (г) чтение общих реестров данных; (д) публичный API модуля, зарегистрированный в ModuleRegistry. Оркестрацией занимаются ТОЛЬКО координаторы (§8) — глобальные модули, которые управляют всеми остальными.

**П5. Максимум неизвестности.** Системы обязаны корректно работать с контентом, о котором не знают заранее: новые типы предметов, новые статы, новые теги, новые условия, новые комбинации ривен-модификаторов. Никаких `switch` по конкретным id; только словари, теги, условия и обобщённые обработчики. Неизвестные данные — не ошибка, а рядовой случай: проигнорировать, показать по месту или отложить — по правилу конкретной системы.

**П6. Числа — в данных, шансы — на стол.** Ни одного магического числа в логике (всё в `content/balance/`). Все шансы, влияющие на игрока, честно показываются в UI числом. Гейты не прячутся: заблокированное видно с условием открытия.

## 5. Слои и структура проекта

```
src/
  kernel/                       # ЯДРО: не знает ни одной игры
    di/                         #   service-container.ts — DI-контейнер
    bus/                        #   stat-bus/, event-bus/, price-bus/, rng-bus/
    services/                   #   pity/, transaction/, task-registry/, stats/
    time/                       #   time-service.ts, offline-catchup.ts
    save/                       #   save-director.ts, migrations.ts
    content/                    #   content-registry.ts, validation.ts (zod)
  shared/
    types/                      #   ids.ts, tags.ts, result.ts, requirement.ts
    utils/                      #   rng.ts, math.ts, format.ts
  modules/                      # ИГРОВЫЕ МОДУЛИ M01–M18 (изолированы)
    <module-id>/
      manifest.ts               #   id, версия, API, события, провайдеры
      logic/                    #   чистые функции + сервисы (1 файл = 1 задача)
      state/                    #   собственный срез состояния модуля
      data/                     #   контент модуля (json/ts)
      tests/                    #   *.spec.ts
  content/                      # КОНТЕНТ (не код)
    balance/                    #   ВСЕ числа: energy.ts, shop.ts, forging.ts...
    items/ crops/ fish/ mobs/ passives/ quests/ village/ locale/
  app/                          # КООРДИНАТОРЫ
    director/                   #   game-director.ts, module-lifecycle.ts
    bootstrap.ts
  ui/                           # UI (фаза 6): панели, mini-games/, tooltips/
  debug/                        # debug-консоль (фаза 0): команды текстом
```

Правила слоёв: `kernel` не импортирует ничего выше себя; `modules` импортируют `kernel` и `shared`, но НЕ друг друга; `app` импортирует всё и монтирует модули; `ui` импортирует `modules` только через публичный API и шины.

## 6. Правила файлов (свойство — единственное)

- **Один файл = одна ответственность.** Файл `shop-rotation.ts` делает ротацию и ничего больше. Схемы отдельно от логики, логика отдельно от данных, данные отдельно от UI.
- **> 300 строк — жёлтый флаг.** При следующем касании файла распилить по ответственностям.
- **> 500 строк — красный флаг.** Рефакторинг обязателен ДО мержа. Это правило проверяется на ревью каждого сеанса.
- **Целевой размер — 50–250 строк.** Средний файл по проекту должен попадать в этот коридор.
- Пилим по смыслу, а не механически: типы → `types.ts`, один сценарий → один файл, тест одного сценария → один `spec.ts`.
- Имена: файлы `kebab-case.ts`, типы `PascalCase`, функции/поля `camelCase`, статы — точечные id (`player.energy.max`), контент-id — `snake_case`.

## 7. Правила коммуникации модулей

Разрешено модулю:
1. `publish`/`subscribe` на EventBus (типизированно; каталог событий — `02-BUSES §4`).
2. `resolve` у StatBus / PriceBus / RngBus — чтение итоговых чисел.
3. `register(task)` / `runTask(systemId)` в TaskRegistry — если модуль предоставляет или заказывает автоматическую работу.
4. Регистрировать `ModifierProvider` в StatBus (свои бафы — отдаёт свои модификаторы по запросу шины).
5. `ModuleRegistry.get(id).api.<method>()` — вызов публичного API другого модуля через реестр (не прямой импорт!).
6. Читать общие таблицы `content/` и счётчики `stats`.

Запрещено модулю:
- `import` любого другого игрового модуля (прямое нарушение изоляции);
- знать структуру ЧУЖОГО состояния;
- мутировать базы (П2);
- держать логику другой системы «у себя».

## 8. Координаторы (слой `app/director/`)

Глобальные модули, которые одни знают обо всех. Каждый — маленький файл с единственной обязанностью:

- **GameDirector** — включает/выключает модули, задаёт порядок тиков, монтирует модули в реестры.
- **TimeDirector** — гоняет тики, раздаёт `minuteTick/hourTick/dayTick`, запускает оффлайн-досчёт.
- **SaveDirector** — собирает сейв из вкладов модулей (каждый модуль сам сериализует свой срез), применяет миграции.
- **WorkersDirector** (фаза 3) — сопоставляет задачи работников с исполнителями из TaskRegistry: работник «хочет полить ферму» → директор берёт зарегистрированный исполнителем навык `farm.water` и вызывает его. Ни работники, ни ферма друг о друге не знают.
- **UiBinder** (фаза 6) — подписывает панели UI на события и API модулей.

## 9. Манифест модуля (обязателен для каждого)

```ts
// modules/farm/manifest.ts
export const farmManifest: ModuleManifest = {
  id: 'farm',                    // совпадает с M-номером в ROADMAP
  version: '1.0.0',
  stateKey: 'farm',              // ключ среза в сейве
  publicApi: ['farm.plant', 'farm.harvest', 'farm.waterTile', 'farm.upgrade'],
  eventsPublished: ['farm.cropHarvested', 'farm.tileChanged', 'farm.weedsAppeared'],
  eventsSubscribed: [{ event: 'time.hourTick', handler: 'onHourTick' }],

```

Манифест — единственное место, где модуль декларирует ВСЕ свои точки интеграции. Координаторы читают манифесты и монтируют модуль автоматически. Новая интеграция без записи в манифесте — запрещена.

## 10. Definition of Done модуля (проверять каждый сеанс)

- [ ] Логика — чистые функции/сервисы в `logic/`, покрытие тестами критичных путей (шансы — монте-карло, экономика — инварианты).
- [ ] Ни одного числа баланса в коде — всё в `content/balance/`.
- [ ] Все читаемые числа через шины; все изменения характеристик — модификаторами через провайдер, а не мутацией.
- [ ] Манифест заполнен и соответствует фактическому коду.
- [ ] Прямых импортов между игровыми модулями — 0.
- [ ] Срез сейва сериализуемый, версия bumped, миграция написана.
- [ ] Debug-команды модуля добавлены (см. `02-BUSES §12`).
- [ ] Ни один файл модуля не больше 500 строк; новые > 300 — распилены.
- [ ] Отчёт сеанса: список файлов, решения `[DECISION]`, вопросы `[QUESTION]`.

# 02 — ШИНЫ и сервисы ядра

> Подавать вторым в КАЖДУЮ сессию. Этот файл — контракт ядра: все шины, общие сервисы и их правила. Ядро строится в фазе 0 и ПОТОМ НЕ ПЕРЕПИСЫВАЕТСЯ: модули могут только пользоваться контрактами и регистрировать провайдеров. Изменение этого файла = отдельное ревью заказчиком, а не решение AI на месте.

## 1. Инвариант шин

**База не мутируется.** `base` любого параметра хранится в данных и читается ТОЛЬКО шиной при резолве. Любое влияние на число (предмет, навык, пассивка, баф, улучшение, скидка, погода, страх) выражается `Modifier`-ом, который шина находит, агрегирует и возвращает итог. Потребитель никогда не знает, ЧТО повлияло на число — он получает готовый результат. Это делает любую комбинацию источников безопасной и бесконечно расширяемой: новый источник = новый провайдер, ни одна строка существующего кода не меняется.

## 2. Модель модификатора

```ts
type Op = 'flat' | 'inc' | 'more' | 'override' | 'cap';

interface Modifier {
  id: string;                                  // 'passive.node42' | 'forge.card@12' | 'buff.pie7'
  source: { kind: 'item'|'passive'|'buff'|'skill'|'shop'|'worker'|'helper'
                  |'village'|'upgrade'|'debuff'|'event';
            refId: string };                   // кто выдал
  stat: string;                                // 'player.energy.max', 'farm.growthSpeed'
  op: Op; value: number;                       // для cap value = граница
  tags?: string[];                             // контекст-теги: ['fishing','night','layer:3']
  conditions?: Condition[];                    // когда действует (синтаксис — 03-DATA §2)
  stackGroup?: string;                         // в группе берётся max, остальные игнорируются
  priority?: number;                           // для override: побеждает max(priority)
  duration?: { kind: 'ticks'|'seconds'|'days'|'runs'; value: number }; // иначе постоянно
}
```

- `flat` — прибавка к базе; `inc` — процент, складывается с другими `inc`; `more` — процент, перемножается отдельно (как в POE: increased складываются, more умножается каждый сам по себе); `override` — полная замена значения (побеждает высший приоритет); `cap` — ограничение результата сверху или снизу.
- Баф «+30% скорости роста на 10 минут» — Modifier с `duration`. Дебаф «замёрз в холодном слое: −50% урона» — Modifier с `conditions: [{t:'ctxTag', tag:'status:cold'}]`. Отдельных систем бафов/дебафов НЕ СУЩЕСТВУЕТ — всё модификаторы.
- **[ИЗМЕНЕНО 2026-10-22]** Срок модификатора хранится абсолютной датой `expiresAt` (инвариант §8 «все таймеры — абсолютные даты»); `duration` остаётся декларативной формой ввода и компилируется в `expiresAt` при создании. Для `kind: 'runs'` дата НЕ выставляется: баф живёт до конца забега, sweep его не трогает, очистка — API модуля-владельца (M13). Ратифицировано по аудиту Фазы 0.

## 3. StatBus — шина характеристик

```ts
resolve(query: { stat: string; ctx: ResolveCtx }): number
// псевдокод резолва:
//   1. base = contentRegistry.base(query.stat)               // база из данных, НИКОГДА не меняется
//   2. mods = providers.flatMap(p => p.provide(query))       // все зарегистрированные провайдеры
//          .filter(условия и теги подходят под ctx)
//          .applyStackGroups()                               // внутри стек-группы — max
//   3. v = hasOverride(mods) ? maxPriority(mods).value : base
//   4. v += sum(flat);  v *= (1 + sum(inc)/100);
//      for each more: v *= (1 + more/100)
//   5. v = applyCaps(v);  return round(по правилам округления stat'а)
```

Пример трассировки (энергия): база `player.energy.max = 100`; пассивка «+20 flat»; keystone «Спартанец» — `override 50` с высоким приоритетом; улучшение «Кровать» — `inc +10%`. Резолв: override побеждает → 50; flat-прибавки в этой ветке не применяются (замена есть замена) → итого 50. Потребитель (M01) получил 50 и не знает, кто на это повлиял.

**[УТОЧНЕНО 2026-10-22]** Стек-группа — правило ВЫЖИВАНИЯ модификатора (внутри группы max, §2), а не правило арифметики: все выжившие моды применяются по своему op. Пример: база 100; два `inc 25` в разных группах → оба выживают → `100 × (1 + (25+25)/100) = 150`; два `more 25` в разных группах → `100 × 1.25 × 1.25 = 156.25`; оба мода в одной группе → выживает max(25) → 125 в обоих случаях. Групповое умножение для `inc` НЕ вводится — это был бы дубликат `more` + stackGroup. (Erratum FIX-PHASE-0 §C: строка приёмки «inc в разных группах → 156.25» — ошибка транскрипции; реализация ядра верна. Ратифицировано заказчиком 2026-10-22.)

Правила StatBus:
- Провайдеры регистрируются модулями при активации (манифест `modifierProviders`) и лениво опрашиваются при каждом резолве: провайдер сам решает, какие модификаторы он даёт под конкретный запрос (экипированный предмет перечисляет свои роллы; пассивки — выделенные узлы; работник — свои трейты по назначению).
- Кэш: результат резолва кэшируется до конца тика или до события `invalidate.stat`. Часовые пересчёты — дёшево.
- `resolve` — чистая функция от (данные + состояние провайдеров + ctx): одинаковый вход даёт одинаковый выход (тестируемость).

## 4. EventBus — шина событий

Типизированный pub/sub. Модуль публикует СВОИ события (манифест `eventsPublished`) и подписывается на чужие ТОЛЬКО через манифест `eventsSubscribed`: прямых ссылок нет, порядок вызова обработчиков не гарантирован, отменить чужое событие нельзя.

Базовый каталог ядра (модули расширяют своими, имя = `<модуль>.<сущность>.<действие>`):

| Событие | Когда |
|---|---|
| `time.minuteTick` / `time.hourTick` / `time.dayTick` | каждую игровую минуту / реальный час / сутки |
| `player.energySpent` / `player.hpChanged` / `player.levelUp` / `skill.levelUp` | игрок M01 |
| `wallet.transaction` | любая транзакция (золото, ресурсы) |
| `item.acquired` / `item.consumed` / `item.equipped` / `item.sold` | инвентарь M02 |
| `shop.purchased` / `shop.rotated` | магазин M04 |
| `farm.cropHarvested` / `farm.weedsAppeared` / `farm.tileChanged` | ферма M05 |
| `pen.produceCollected` | загон M06 |
| `fish.caught` / `cast.completed` | рыбалка M07 |
| `lake.bred` / `lake.fishSick` | озеро M08 |
| `craft.completed` | крафт M09 |
| `modforge.rolled` | ривен-движок выдал роллы: стартовые роллы предметов, рероллы, карточки заточки, трейты (M03; потребители — M02/M10/M11/M13) **[ДОБАВЛЕНО 2026-10-23]** |

## 5. PriceBus — шина цен

Вся экономика ходит через `PriceBus` (`04-DISCOUNTS` описывает ИСТОЧНИКИ скидок; здесь — механика):

```
buyPrice(defId, ctx)  = round( base × (1 + sum(markup)) × (1 − gGlobal) × (1 − gLocal) )
  gGlobal = min(capG, sum(глобальных скидок на defId/категорию))   // внутри группы складываются
  gLocal  = min(capL, sum(локальных скидок игрока))
  итоговая скидка ≤ maxTotal (90%); цена ≥ ceil(base × 0.1) — бесплатно ничего не бывает
sellPrice(defId, ctx) = round( base × sellRate(0.40 базово) × (1 + sum(sellBonus)) )
```

Редкость и качество экземпляра входят в `base` множителями (03-DATA), скидки применяются к уже смультиплицированной базе. Ни один модуль не имеет права считать цену сам — только `priceBus.buy/sell`.

## 6. RngBus — шина рандома

- Детерминированный PRNG (xoshiro128 или mulberry32) с явным сидом. **dailySeed = hash(saveId + dateISO)** — магазин, доска работников, биржа и daily-квесты роллятся одинаково весь день; перезапуск игры перероллов не даёт.
- `roll(table, ctx)`: взвешенный выбор из `{ id, weight, lucky? }` с удачей: **[ИЗМЕНЕНО 2026-10-22]** эффективный вес = `weight × (1 + luck(stat, ctx)/100)` применяется ТОЛЬКО к записям с флагом `lucky: true` (равный множитель на все веса — математический no-op из-за нормировки; поправка аудита Фазы 0). Итоговые веса нормируются; `luck = −100` обнуляет вес lucky-записей — никаких отрицательных весов и NaN. luck — модификатор шины (удочка тянет `fishing.luck.rare`, факел — `mine.luck.hidden`, наживка — свою категорию).
- `rollRange(min, max, curve)` — равномерно / треугольно / степенно.
- Все роллы, влияющие на игрока, логируются — debug-команда `roll.log` и честные UI-таблицы шансов строятся на этом логе.

## 7. PityService — счётчики жалости

Универсальные именованные счётчики: `pity.get(ownerId, key)`, `pity.bump(ownerId, key)`, `pity.reset(ownerId, key)`. Правила сброса задаёт потребитель (M10: bump при провале, reset при успехе). Ядро только хранит — логику жалости модуль описывает у себя в данных.

## 8. TimeService — время, тики, оффлайн

- Тик ядра — 1 игровая минута = 1 реальная секунда (настройка в данных). При открытом табе — setInterval; часовые/дневные границы — по РЕАЛЬНОМУ календарю игрока: `dayTick` в 00:00 локального времени (ротации магазина, работников, биржи, квестов), `hourTick` — каждый реальный час (сорняки, продукция животных).
- Все таймеры в игре — АБСОЛЮТНЫЕ даты (`grownAt`, `endsAt`), а не остатки тиков.
- **Оффлайн-досчёт `catchUp(lastSeen → now)`:** (1) пересчитать абсолютные таймеры и производные состояния (грядки READY, продукция накоплена до склад-cap); (2) часовые правила циклом, кап 72 итерации; (3) дневные правила циклом, кап 14 итераций (работники отработали по своим расписаниям); (4) собрать `offlineReport`. Защита от отмотки часов: `lastSeen > now → lastSeen = now`.

## 9. TransactionService — атомарные операции

Единственный способ тратить/получать валюты и предметы: `transact({ costs[], grants[], eventId })`. Проверяет всё (цена через PriceBus, наличие), затем списывает и выдаёт ЦЕЛИКОМ или отказывает (`Result`), публикует `wallet.transaction` и события гранта. Модули не пишут в кошелёк напрямую.

## 10. TaskRegistry — реестр исполнителей

Паттерн «модули не знают друг друга, но работники могут выполнять их работу»:

```ts
// ферма (M05) при активации регистрирует исполнителей:
taskRegistry.register('farm.water', { run: (ctx) => ... })   // и 'farm.weed', 'farm.harvest'...
// работники (M11) НЕ импортируют ферму: WorkersDirector берёт
// свободный executor 'farm.*' из реестра и вызывает run(ctx)
```

Исполнитель сам публикует события (`worker.actionDone` с указанием системы) — ферма узнаёт, что «кто-то полил», из события, а не из чужого кода. Так же подключаются жители деревни («помощь с задачками») и автоматика улучшений (спринклеры).

## 11. SaveDirector — сейв

Формат: `{ saveVersion, savedAt, saveId, modules: { [stateKey]: unknown } }`. Каждый модуль сериализует ТОЛЬКО свой срез (манифест `stateKey`) чистыми данными (никаких классов и функций). Миграции — цепочка `migrations.ts` по версиям: любое изменение схемы = bump версии + миграция. Автосейв раз в 30 с + на `visibilitychange`. Экспорт/импорт JSON.

## 12. DebugConsole — консоль отладки (фаза 0, живёт до конца проекта)

Текстовые команды (поле ввода в углу экрана), пока нет UI:
`give <defId> [qty]` · `mod add <stat> <op> <value>` · `resolve <stat>` · `price <defId>` · `time +N<h|d>` · `shop.reroll` · `forge force <success|fail|rollback>` · `roll <tableId>` · `pity show` · `save export` · `save import <json>` · `catchup simulate <hours>` · `mobs list`.

**[ИЗМЕНЕНО 2026-10-22]:** `mod add` понимает ключи `[prio=N] [group=X] [tag=T]` — ручные пробы приоритетов, стек-групп и тегов; `events ticks on|off` — показ `time.minuteTick` в отладочной ленте (фильтр СТРОГО отображения: подписчики события не затрагиваются). Все now()-зависимые элементы UI рендерятся только после монтирования (hydration-инвариант).

Каждый модуль ДОБАВЛЯЕТ СВОИ команды через манифест — это и есть «интерфейс» фаз 0–5 наряду с минимальными отладочными панелями (таблицы состояния без красоты).

## 13. Обязательные тесты ядра (фаза 0, критерий приёмки)

1. Aggregation: `(base + flat) × inc × more` на 10+ комбинациях; override, cap; стек-группы.
2. Провайдеры: регистрация/снятие, ленивый опрос, инвариант чистоты resolve.
3. Pity: bump/reset/границы.
4. RNG: воспроизводимость по сиду; luck смещает веса в нужную сторону (монте-карло, допуск по хи-квадрат).
5. Транзакции: атомарность, отказ при нехватке, публикация событий.
6. catchUp: фиксированные даты через DI-подмену `now()` — грядки/продукция/дневные ротации.
7. Сейв: roundtrip + миграция версии N → N+1.
8. TaskRegistry: регистрация/вызов/отсутствие исполнителя — штатный отказ.

## 5. Ривен-конструктор (M03) — типы


# M01 — Игрок: энергия, HP, кошелёк, XP/уровень, навыки

> Фаза 1 · объём M · вход: 01-CORE, 02-BUSES, 03-DATA, этот файл. Зависимости: только ядро.

## 1. Цель модуля

Быть единственным владельцем «тела игрока»: энергии, HP, кошелёка ресурсов, опыта и уровня, навыков от использования. Всё, что другие модули хотят списать или выдать игроку, идёт через TransactionService и события — сам кошелёк инкапсулирован здесь.

## 2. Энергия

- Базы в данных: `player.energy.max = 100`, `player.energy.regenPerMinute = 1/3` (1 ед / 3 мин), реген идёт и оффлайн (catchUp), но не выше капа.
- Кап растёт модификаторами: пассивки (`+20 flat` на пороге), «Кровать» (раз в игровой день бесплатный сон до капа — действие из данных), еда (`useAction` из M02 даёт `grantEnergy`).
- Расходы действий — статы вида `action.<system>.<verb>.energyCost` с базами в `content/balance/energy.ts`: вспашка 5, посадка 1, полив 2, прополка 1, сбор 3, заброс 4, кормление 1, вход в шахту 20, удар в бою 1, крафт 2, попытка заточки 3. Списание: `statBus.resolve('action.farm.plow.energyCost')` → TransactionService. Keystone «Спартанец» (M14) опустит всё это через `inc −50%` — модуль не узнает.
- Правило дизайна: энергия — темпоритм, не замок. Всегда есть занятия с нулевым расходом (магазин, приказы работникам, биржа), и еда.

## 3. HP

- Базы: `player.hp.max = 50`, реген вне шахты `1 / 5 мин`; в шахте НЕ регенится (родники/костры/зелья — M13).
- `useAction` лечит мгновенно. «Смерть» (HP = 0 в забеге): событие `player.hpChanged` с тегом `death` — M13 сам решает, что делать (вылет, потеря 20% рюкзака, HP = 1). M01 только хранит и репортит.

## 4. Кошелёк (ресурсы) и XP/уровень

- `wallet: Record<CurrencyId, number>` — золото, руды, материалы, хозяйство (`03-DATA §1`). Пополнение/списание ТОЛЬКО через TransactionService; событие `wallet.transaction` с раскладом. Для каждого ресурса в контенте — `sources/sinks` (данные для подсказок «где добыть»).
- **[УТОЧНЕНО 2026-10-22]** Физическое хранение кошелька — сервис ядрового слоя (срез `kernel.wallet`, сдан в Фазе 0 и заморожен вместе с TransactionService). Модуль M01 НЕ переносит срез и НЕ дублирует хранение: он владеет игровой семантикой кошелька — каталог валют и `sources/sinks` в контенте, публичный API грантов/списаний (обёртки над TransactionService), инвариант «ни один модуль не пишет в кошелёк напрямую» (§8). Ратифицировано по итогам аудита Фазы 0 + FIX-0.1.
- XP: за значимые действия, начисляется по событиям (таблица в данных: вспашка 2, сбор 5, рыба 8, крафт 10, моб 15, босс 100, квест 50–500). Уровень: `xpToNext(L) = 100 × 1.15^L`. Событие `player.levelUp` — на него подписаны пассивки (+1 очко, M14), гейты, UI.
- Уровень игрока — главный гейт разблокировок; проверяется везде через `Requirement`-оценщик.

## 5. Навыки от использования

- Список навыков в данных: Фермерство, Рыболовство, Рыбоводство, Животноводство, Крафт, Кузнечество, Горняк, Боец, Торговля.
- Механика: значимое действие публикует событие с тегом навыка (например `farm.cropHarvested` → `skill:farming`); SkillEngine по манифесту подписок добавляет XP. Заточка даёт опыт кузнечеству ДАЖЕ при провале — стаж есть всегда.
- `xpToNext(skillLevel) = 50 × 1.2^skillLevel`. Каждый уровень навыка — модификатор из `SkillDef.perks` (данные): «+5% эффективность смежных действий», каждые 5 уровней — перк-порог (шире зоны мини-игр, +1 слот грядки/озера на больших порогах, разблокировка локаций: навык 10 рыболовства открывает Реку).
- Все перки навыков — провайдер `skillProvider` в StatBus: сам модуль не раздаёт эффекты руками.

## 6. Счётчики ядра (stats)

Ядро ведёт `Record<counterId, number>` по событиям (конфиг счётчиков в данных): урожаи по типам, рыбы по видам, попытки заточки, успехи/откаты, забеги, боссы по типам, объёмы торгов. Потребители: квесты/ачивки (M15), биржевые тренды (M16), пассивные очки. Счётчик = данные (`{ id, event, filter }`) — на новую статистику код не пишется.

## 7. Интеграция (манифест)

- События публикует: `player.*`, `skill.levelUp`, `wallet.transaction` (гранты TransactionService читает).
- Провайдеры: `skillProvider`, `levelBonusProvider` (+HP/энергия за уровень).
- API: `player.spendEnergy`, `player.checkHp`, `player.addXp`, `skills.get`.
- Debug: `give`, `xp add <n>`, `energy set`, `skills list`, `stats show`.

## 8. Приёмка и тесты

- [ ] Ни один модуль не пишет в кошелёк напрямую (тест-шпион на wallet-объект).
- [ ] Реген энергии/HP в catchUp совпадает с ручным расчётом по фиксированным датам.
- [ ] XP-кривые и перки — из данных; тест уровня с 1 по 60.
- [ ] Энергия списывается один раз за действие, при отказе транзакции — откатывается.
- Границы: инвентарь — M02; ачивки — M15; объекты «сон/еда» — данные M02/M05.

# M02 — Инвентарь, экипировка, качество предметов

> Фаза 1 · объём M · вход: 01-CORE, 02-BUSES, 03-DATA, M01, этот файл. Зависимости: M01.

## 1. Цель модуля

Владеть экземплярами предметов: хранить, стакать, экипировать, продавать, расходовать. Быть провайдером модификаторов экипировки в StatBus. Роллы характеристик — НЕ здесь (генерирует M03), здесь только хранение и применение.

## 2. Слоты, стаки, вкладки

- Сетка: база 20 слотов (`player.inventory.slots`), расширение «Рюкзаками» (кожевенный крафт M09) и пассивками: +4 за шаг, кап 60. Стаки: семена/наживки/расходники/рыба — до 50 (апгрейд до 100); уникальное снаряжение не стакается.
- Вкладки по `itemType` — из данных (инструменты/снаряжение/расходники/прочее); категория новой вкладки = строка данных.
- Слоты экипировки (данные): Кирка, Оружие, Броня, Щит, Удочка, Активная наживка, Аксессуар ×2. Новые слоты (будущее) — без кода.

## 3. Действия над предметом

Использовать (consumable: `useAction`-эффекты через TransactionService/M01), Экипировать/снять, Продать (`priceBus.sellPrice` + TransactionService, событие `item.sold`), Заточить (вызов API M10, не импорт!), Разобрать (вернуть 25% ресурсов рецепта), Подарить (M16 через флаг тега `giftable`).

Гейты: использование/экипирование проверяет `ItemDef.requirements` (уровень, навык, ачивка, флаг). Нарушение — штатный отказ `Result` с причиной (UI покажет).

## 4. Качество, редкость, прочность

- `quality: { tier, value }`: тир D..SS, дробное 0..100 внутри тира для сверки цен. Для крафтового снаряжения тир пересчитывается от `sharpeningLevel` (M10: каждые 10 уровней = +1 тир). Для выпавшего/выловленного/выращенного — роллится при получении (RngBus, из данных таблицы).
- Сила статов и цены — множители тиров/редкости применяются К БАЗЕ шиной (П2): `base(price)` уже содержит множители, потребители про них не знают.
- Прочность: −1 за использование у tool/weapon/armor/shield/rod; при 0 предмет «сломан» (не работает, НЕ исчезает); ремонт на наковальне (M09) за 10% базовой цены. Прочность — поле экземпляра, НЕ модификатор.

## 5. Провайдер модификаторов экипировки

`equipmentProvider`: при резолве любого стата перечисляет экипированные `ItemInstance.rolledMods` (+ стартовые `baseStats` шаблона как flat-модификаторы с источником item) и отдаёт их шине. Смена экипировки → `invalidate.stat`. Так «меч +10% крита» влияет на бой (M12) без единого импорта между модулями.

## 6. Интеграция

- События: `item.acquired/consumed/equipped/sold` (в `item.acquired` — defId, качество, источник-тег: для квестов «поймай/вырасти/скрафти»).
- API: `inventory.add/remove/has`, `inventory.equip/unequip`, `inventory.list(filter)`.
- Debug: `give`, `inv list`, `inv equip <iid> <slot>`, `inv clear`.

## 7. Приёмка и тесты

- [ ] Экипирование предмета с роллом меняет `resolve` нужного стата (интеграционный тест с ядром).
- [ ] Гейт-требование блокирует экипировку и показывается причиной отказа.
- [ ] Стаки сливаются/делятся по правилам данных; переполнение — отказ, не потеря.
- [ ] Продажа идёт через PriceBus/TransactionService: событие `wallet.transaction` и `item.sold`.
- Границы: генерация роллов — M03; заточка — M10 (только через `ModuleRegistry.get('forging')`); UI — фаза 6.

# M15 — Квесты, ачивки, гейты (движок условий)

> Фаза 2 · объём M · вход: 01-CORE, 02-BUSES, 03-DATA, M01, этот файл. Движок — декларативный: НИ ОДНОГО обработчика конкретного квеста или ачивки в коде; только данные + счётчики ядра + события.

## 1. Цель модуля

Три сущности на одном движке: ежедневные и еженедельные квесты (из пулов по dailySeed), сюжетные цепочки (шаги открывают системы), ачивки (счётчики → награды → `unlockFlags`-гейты для магазина/рыб/слоёв/систем). Прогресс трекается ИСКЛЮЧИТЕЛЬНО по событиям шины.

## 2. Движок

- `QuestDef` / `AchievementDef` (03-DATA §9): шаги с `condition: Condition` и наградами `Reward[]`.
- Подписки манифеста: события из каталога (02-BUSES §4) → счётчики ядра (M01 §6) → переоценка активных условий. Условие — общим `Condition`-оценщиком (03-DATA §2): `{t:'any'}` по «собрано урожаев ≥ N», «поймано рыб X ≥ K» (фильтр по defId), «успешных заточек ≥ M», «продано на бирже ≥ J золота».
- Новая механика даёт квестам прогресс автоматически: если модуль публикует событие — квест-шаблон с фильтром по нему просто добавляется ДАННЫМИ.
- Награды: через TransactionService + `passivePoint` (событие для M14) + `flag` (в ачивках) + `xp`.

## 3. Ежедневные и еженедельные

- Daily: 3 квеста роллятся в 00:00 из пула ~30 шаблонов («Собери 20 единиц урожая», «Поймай 5 рыб», «Сделай 3 попытки заточки», «Пройди 1 забег шахты», «Накорми всех рыб»). Награды: золото + XP + сундучок ресурсов. 1 бесплатная замена квеста в день (кнопка — данные).
- Weekly: 3 квеста-цепочки из 3–4 условий, крупные награды: уникальные предметы, очки пассивок, купоны магазина.
- Прогресс дня не переносится; невзятые награды пропадают (мягко: напоминание в 22:00 — событие для UI).

## 4. Цепочки (сюжетные)

- «Восстановление хутора» — обучающая: 15 шагов (первая вспашка → первый работник → первый босс), шаги открывают системы по очереди — главный источник «гейтов по мере прохождения». Шаг цепочки может: выдать предмет, разблокировать систему (`flag`), показать страницу текста (данные).
- «Тайна глубин» (шахта, кульминация на боссе слоя 5), «Гость с озера» (мутации), «Соседи» (подготовка к деревне).
- Завершение цепочки — церемониальное событие (данные для UI-экрана).

## 5. Ачивки

- `AchievementDef`: условие по счётчикам, награды, `unlockFlags` — флаги, на которые смотрят гейты M04 (ассортимент), M07 (рыбы), M12 (слои), M16 (жители).
- Стартовый набор ~40 в `content/achievements.ts`; hidden-ачивки (пасхалки) поддерживаются.
- Примеры: «Первый улов» (поймать 1 рыбу — гейт наживок), «Хозяин озера» (вывести рыбу A+ — гейт «Ледяной нерки»), «Глубины» (убить босса слоя 3 — гейт «Древнего сома»), «Агроном» (100 урожаев — гейт солнечника), «Постоянный клиент» (100 покупок — скидка 04-DISCOUNTS).

## 6. Интеграция

- События: `quest.progress/completed`, `achievement.unlocked` (id, name, rewards — для тостов и журнала).
- API: `quests.list(type)`, `quests.claim(id)`, `quests.rerollDaily(id)`, `quests.chainProgress(chainId)`.
- Провайдер: `questFlagsProvider` — флаги, которые сами что-то модифицируют (редко; обычно флаги читают гейты-оценщики).
- Debug: `quests roll`, `quests complete <id>`, `ach unlock <id>`, `flags list`.

## 7. Приёмка и тесты

- [ ] Ноль спец-обработчиков: добавление нового квеста/ачивки в данных поднимает прогресс без пересборки (интеграционный тест).
- [ ] Daily детерминирован по dailySeed; замена — 1/день; после `time +1d` — новый набор.
- [ ] Флаг ачивки открывает реальный гейт: тест с фикстурой магазина (item с `unlock: achievement`).
- [ ] Цепочка: шаги идут строго последовательно; награды выдаются один раз (идемпотентность).
- Границы: счётчики — ядро/M01; UI-журнал — фаза 6; контент цепочек фаз 3–5 добавляется по мере систем.

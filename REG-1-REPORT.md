# REG-1 — Живой реестр: авто-расширяемые списки без ручного занесения

> Сеанс по запросу спеки между M12.1 и M12.2:
> «давай уже сейчас сделаем динамический авто расширяемый список — 1) команд 2) Шин 3) Сервисов 4) всех M01–M15 5) Модулей и всего подобного, чтобы не вручную все заносить, а как-то автоматом (возможно уже где-то это работает). ЕСЛИ ЭТО МОЖНО просто и красиво сделать. Если нельзя, то не надо делать».

## 1. Ответ на запрос

**Можно. Сделано просто и красиво — «живой реестр»: одна команда `registry`, ноль ручных таблиц.**
Каждый список читается из рантайм-реестра в момент показа: новый модуль / команда / сервис /
контент-таблица появляются в витрине **сами** в момент регистрации.

«Возможно уже где-то это работает» — да: `help` (реестр команд), `modules` (реестр модулей),
`stats.list` (каталог статов) и подсказки ввода консоли всегда были динамическими. Недоставало
витрины шин/сервисов и M-номеров — она добавлена тем же паттерном.

### Что показывает `registry [раздел]`

| Раздел | Источник (живой) | Что видно |
|---|---|---|
| `модули` | `ModuleRegistry.list()` + манифесты | M01–M15 по возрастанию: версия, api, события +/−, провайдеры, исполнители, срез |
| `шины` | интроспекция Фазы 0 | EventBus: подписки/имена; StatBus: статы + провайдеры поимённо; PriceBus: провайдеры; RngBus: таблицы |
| `сервисы` | объектные поля инстанса `Game` | 17 полей с именами классов (новый сервис ядра виден без правок витрины) |
| `команды` | реестр консоли (тот же, что у `help`) | всего + группы по префиксу |
| `контент` | `ContentRegistry.tableNames()` | 49 таблиц реестра 03-DATA §11 |

Живой снимок текущей игры: модули 13 (M01–M12, M15), статов 81, провайдеров StatBus 14,
подписок EventBus 90 по 35 именам, событий в манифестах 42, команд 133, контент-таблиц 49.
M13/M14 появятся в списке автоматически, когда будут собраны.

## 2. Как это сделано

| Файл | Изменение |
|---|---|
| `src/game/module-registry.ts` | `ModuleManifest += title?: string` — человекочитаемое имя с M-номером (ROADMAP 00-README §2), опциональное, аддитивное |
| `src/game/modules/*/manifest.ts` ×13 | `title` при рождении модуля — **единственное** место, где M-номер заносится (манифест = единая декларация, 01-CORE §9) |
| `src/debug/registry-overview.ts` **NEW** | чистая функция `buildRegistryOverview(game, commands)` — весь агрегатор; `byManifestTitle` — сортировка M01…M15 |
| `src/debug/commands-registry.ts` **NEW** | команда `registry [модули\|шины\|сервисы\|команды\|контент]` — только форматирование |
| `src/debug/console.ts` | монтаж регистратора одной строкой (composition root) |
| `src/debug/commands-core.ts` | витрина `modules`: M-номера + сортировка |
| `src/selfchecks/registry-checks.ts` **NEW** | группа «Реестр · живой обзор (registry)» ×7 |
| `src/selfchecks/runner.ts` | аппенд группы в конец (канон-дифф = чистое добавление) |

Инварианты группы «Реестр» ×7: title-формат/уникальность/сортировка; согласование счётчиков со
своими реестрами; агрегат событий = манифестам; шины байт-в-байт с живыми API; контрактные
сервисы 02-BUSES на месте; сумма групп команд = total. `getCommandRegistry` подтягивается
динамическим импортом — разрыв цикла `runner → registry-checks → console → commands-core → runner`.

## 3. Честная граница: что НЕ автоматизировано и почему

**Авто-дискавери файлов (магия `require.context`-стиля) отклонён** — не «просто и красиво»
в этом стеке:

1. Turbopack (дефолт Next 16) не поддерживает `require.context`; игра клиентская — `fs` нет.
2. Порядок монтажа модулей декларативен и важен («после workers до quests») — composition root
   (01-CORE §7) обязан быть явным; это архитектура, а не недоработка.
3. Канон selftest байт-чувствителен к порядку групп — авто-перебор файлов ломает воспроизводимость.

Итог: **1 строка на нового участника** в `console.ts` / `module-wiring.ts` / `content-registration.ts`
/ `runner.ts` остаётся намеренной ценой явного composition root. Все ВИТРИНЫ (списки для человека)
теперь автоматические.

Состав четырёх шин — замороженный контракт 02-BUSES (меньше кода не бывает: растёт наполнение,
не набор).
